En cours de développement

Abstract Analyzer

Plateforme de soumission et de tri d'abstracts scientifiques, générique pour n'importe quel organisateur de conférence, colloque ou journée thématique : soumission en ligne, score de pertinence en temps réel par rapport au thème de l'édition, détection de doublons (toujours validée par un humain), clustering thématique automatisé après la clôture des soumissions, et tableau de bord organisateur.

Statut actuel : single-tenant. Le projet deviendra à terme un SaaS multi-tenant (plusieurs organisateurs sur une même instance), mais cette phase est volontairement reportée : le produit single-tenant est construit et validé en premier.

Fonctionnement

Soumission Dépôt d'un abstract par un auteur, pour une édition donnée
Score de pertinence Similarité vectorielle en temps réel avec le thème de l'édition
Détection de doublons Alerte automatique, validation finale toujours humaine
Clustering post-clôture UMAP + HDBSCAN, hyperparamètres réoptimisés par édition via Optuna
Dashboard organisateur Vue d'ensemble des soumissions, thèmes détectés, doublons à trancher

Architecture backend

Architecture en couches strictes : une couche ne parle jamais directement à la couche n moins 2 (l'API n'appelle jamais un DAO directement). Toute dépendance externe (base de données, base vectorielle, modèle d'embedding) est masquée derrière une interface, remplaçable par configuration sans toucher au code métier.

api (endpoints FastAPI, validation, zéro logique métier)
services (logique métier, orchestre les DAO/providers)
dao (interfaces + implémentations SQLAlchemy)
domain (entités métier pures, sans dépendance framework)
Où en est le code : le domaine, les interfaces DAO/Provider et les modèles ORM sont codés. Une seule implémentation concrète existe à ce jour (le DAO MySQL des abstracts) ; le reste (implémentations DAO restantes, base vectorielle, provider d'embedding, services, couche API) reste à écrire sur ce même patron.

Stack technique

Backend : Python, FastAPI (architecture en couches domain / dao / services / api) · Base relationnelle : MySQL en local, PostgreSQL + pgvector visé au déploiement · Base vectorielle : ChromaDB en local, pgvector au déploiement · Embedding : SPECTER2 (similarité entre documents scientifiques) · Clustering : UMAP, HDBSCAN, Optuna · Frontend : React (squelette) · Outils : uv, Alembic, Docker, pytest
